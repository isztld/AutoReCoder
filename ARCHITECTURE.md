# AutoReCoder — Architecture

Technical reference for contributors and users who want to understand how the system works.

---

## Design Principles

**Correctness is non-negotiable.** The oracle enforces this mechanically: `pass_rate` must
stay at 1.000 throughout the entire migration. Any change that breaks correctness is
automatically reverted.

**Incremental over all-at-once.** Large C codebases cannot be migrated to safe Rust in one
shot — the borrow checker rejects too much at once. AutoReCoder migrates one function per
experiment, always from a working state, always verifiable.

**Signal from failure.** A failed migration attempt is not wasted: `rustc` error codes are
structured signal that narrow down the safe approach. The pattern library captures this
accumulated knowledge across experiments.

## Components

### `oracle.py` — Evaluation Engine (locked)

The locked ground truth. Returns two metrics after every experiment:

```
pass_rate    = matched_inputs / total_inputs   ∈ [0.0, 1.0]
unsafe_count = count of `unsafe` keywords in workspace/src/ (excl. comments/strings)
```

**Key functions:**

| Function | Purpose |
|---|---|
| `count_unsafe(src_dir)` | Count `unsafe` keywords across all `.rs` files, excluding comments and string literals |
| `list_unsafe_functions(src_dir)` | Return functions ranked by: leaf-first, then unsafe density |
| `build_c_binary(original_dir, out)` | Build C source with `-fsanitize=address,undefined` |
| `build_rust_binary(src_dir, out)` | `cargo build --release`; extract rustc error codes on failure |
| `run_differential(c_bin, rust_bin, corpus_dir)` | Compare outputs on each corpus input; skip C crashes |
| `run_miri(src_dir)` | Run `cargo +nightly miri test` for UB detection (informational only) |

The oracle is locked after initial setup. Modifying it to change the metrics would defeat the
entire purpose of the system.

### `bootstrap/bootstrap.py` — One-Time Setup

Run once per new C codebase. Idempotent: skips steps already completed.

**Steps:**
1. Detect build system (`CMakeLists.txt` → cmake, `Makefile` → make, etc.)
2. Extract `compile_commands.json` via cmake's native support or `bear` interception
3. Run `c2rust transpile` → generates fully-unsafe Rust in `workspace/src/`
4. Generate `Cargo.toml` + `rust-toolchain.toml` (c2rust output requires nightly features)
5. Verify baseline: compile both binaries, assert `pass_rate == 1.0` on 100 random inputs
6. Generate corpus: 500 inputs via radamsa mutation (or random bytes as fallback)
7. Save expected outputs to `workspace/corpus/expected/`
8. Extract call graph → `workspace/callgraph.json` (used for leaf-first ranking)

After bootstrap, `workspace/corpus/` is locked — never regenerated during a migration session.

**c2rust output note:** c2rust 0.22.x generates `.rs` files but no `Cargo.toml`. Bootstrap
creates one, detecting binary vs. library crates by the presence of `fn main()`. Crate-level
`#![...]` attributes are moved to the root file; module files have them stripped to avoid
conflicts.

### `workspace/src/` — Migration Surface

The Rust codebase the agent iteratively improves. Starts as 100% unsafe c2rust output.
The agent edits this directory, committing after each change.

**Structure after bootstrap:**
```
workspace/src/
├── Cargo.toml          ← generated by bootstrap
├── rust-toolchain.toml ← pins nightly (needed for c2rust's extern_types feature)
└── src/
    ├── main.rs         ← entry point + crate-level attributes
    └── *.rs            ← translated modules (one per C source file)
```

### `workspace/corpus/` — Locked Test Inputs

Generated once by bootstrap, never modified. Contains:
```
workspace/corpus/
├── input_XXXX.bin          ← raw binary inputs (fed to both binaries via stdin)
└── expected/
    ├── output_XXXX.bin     ← expected stdout from C binary
    └── output_XXXX.bin.exit ← expected exit code
```

The oracle compares Rust output against stored expected outputs, not live C output.
This makes the oracle fast and deterministic.

### `patterns/patterns.md` — Pattern Library

Agent-maintained. Records known C→Rust migration patterns with success rates.
Updated after every experiment. The agent consults this before attempting a migration.

**Format:**
```markdown
## Pattern: <name>
**C idiom:** what the C code looks like
**Rust safe equivalent:** the replacement
**Success rate:** N/M
**Common failures:** why this sometimes doesn't work
**Notes:** learned from experiments
```

### `program.md` — Agent Directives

Human-editable per migration session. Defines the experiment loop, constraints, and
done conditions. Read by the agent at session start.

### `results/results.tsv` — Experiment Log

Tab-separated, append-only. One row per experiment (kept and discarded).
Used by `analysis/analysis.ipynb` to visualize progress.

### `analysis/analysis.ipynb` — Progress Visualization

Jupyter notebook that reads `results/results.tsv` and produces:
- Migration progress curve (unsafe_count over time)
- Pattern effectiveness table
- Summary statistics

## Data Flow

```
workspace/original/   (C source)
         │
         ▼  bootstrap.py
workspace/src/        (unsafe Rust baseline)
workspace/corpus/     (locked test inputs)
         │
         ▼  agent loop (program.md)
workspace/src/        (progressively safer Rust)
         │
         ▼  oracle.py
    pass_rate + unsafe_count
         │
    ┌────┴────┐
   keep      revert
    │          │
results.tsv   git reset
patterns.md
```

## Target Ranking

The oracle's `--list-targets` flag returns functions sorted by:

1. **Leaf functions first** — functions that call no other functions in the codebase
   can be migrated in isolation without cascading changes
2. **Unsafe density** — functions with more `unsafe` blocks give more leverage per experiment
3. **Pattern match** — functions matching a known high-success-rate pattern are preferred

Call graph data comes from `workspace/callgraph.json` (generated by bootstrap).

---

## Corpus Design

The corpus uses **stored expected outputs** rather than live C comparison. This:
- Makes the oracle fast (no need to recompile/run C on every evaluation)
- Makes results reproducible (C binary behavior is fixed at bootstrap time)
- Allows the C binary to be absent during migration sessions

Inputs that cause the C binary to crash or hang at corpus generation time are discarded
(they represent C bugs, not useful test cases).

---

## c2rust Integration

c2rust 0.22.x requires:
- **LLVM 16** (LLVM 17+ breaks the C++ AST exporter)
- **Rust nightly-2022-08-08** (pinned in `vendor/c2rust/rust-toolchain.toml`)
- Build only `-p c2rust` to skip `c2rust-refactor` (needs Python 2 codegen scripts)

The c2rust output is 100% unsafe but correct — it preserves C semantics exactly, including
undefined behavior. The migration process makes it safe without changing the observable behavior.
